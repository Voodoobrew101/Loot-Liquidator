# Loot Liquidator — independent numerical profession-mechanics research protocol (v1.0, 2026-10-28)

**Scope:** research/processing-confidence only. The five hourly agents already cover item/output evidence; this is a parallel **mechanics hypothesis** track, not a replacement for their 25–50 first-pass record target. Never write main, production Lua, production TOC, or silently promote a candidate. Read the canonical ITEMDB_CREATION_PROMPT.md, ProfessionMechanicsRegistry.json, WoWRuntimeAPIRegistry.json, observations and assigned record IDs every run.

## Workflow: one concrete, falsifiable mechanism per worker per batch

1. **ASSIGN:** Master owns a disjoint hypothesis queue. Workers use their assigned hypothesis ID and cross-reference current assigned item/output stable keys, which retain existing priority. Focus on skills, knowledge nodes, gear, Resourcefulness, Multicraft, quality transitions, recipe eligibility and actual patch/hotfix changes. Where a hypothesis is blocked, report the exact missing experiment and continue item coverage.
2. **DEFINE:** Specify game mode, expansion, patch build/time window, recipeSpellID, nominal input count, input item IDs/ranks, *explicit* output item IDs/ranks, profession child skillline, node IDs/ranks, gear and recipe stats, character versus saved-alt context, proposed effect target, its units and direction. No wildcard assumption from an empty ID array. Separate occurrence, positive conditional count, unconditional expected count, quality transition, eligibility, expected reagent savings and operation duration.
3. **SOURCE:** Search for original versioned experiment datasets, original TSM conversion evidence with native units, official change notes and reliable independent replications. Save immutable sources/zero-inclusive per-cast histograms or exact aggregate denominators, including unsuccessful casts, actual consumed/saved inputs, quality, all outputs, and sample context. Record conflicting studies and every missing covariate. Do **not** claim experimental validation from an undocumented forum estimate or a model's own low/high endpoints.
4. **COMPARE:** Require genuinely comparable reference and target cohorts, or an explicit verified bridge. Control input/output rank, recipe variant, patch, skill, specialization, gear, profession stats, reagent count and concurrent bonuses. A stat measured only as rating must not be silently interpreted as percentage. Do not pool unknown-patch or different-mode data. A patch event with unknown numerical effect blocks current-Retail correction.
5. **ESTIMATE:** For output i, E_i = total_i / actual completed operations (including zero-output operations); p_i = operations_with_i / completed operations *only if hit counts exist*. Conditional observed min/max require positive cast data and are not guaranteed hard game bounds. To compare two compatible contexts use a **specific** supported transformation (e.g. E_target = E_reference * factor_target / factor_reference when strictly positive and verified). Confidence intervals/uncertainty must be computed from actual evidence, not invented. Independently track numeric confidence and source identity confidence. An observed average is NOT a globally applicable game formula.
6. **VALIDATE:** Test correct per-operation denominator; same-context reproducibility; holdout/independent source; sensitivity to patch, ranks and nodes; all possible outputs; statistical uncertainty; no double probability multiplication; quality mass conservation; no impossible output unlock; Resourcefulness as INPUT consumption, not extra GEM output. For uncertainty/absent controls, leave candidate BLOCKED/EMPIRICAL_ESTIMATE with concrete missing data. Do not fill null with 0 or 1. The 90/100 score denotes evidence strength, not accuracy percentage.
7. **SUBMIT/QA:** Workers append immutable worker-specific evidence/report files (under research/evidence/observations/ and research/coordination/submissions/<worker>/) with hypothesisID, sources, sample count, matched conditions, candidate formula, units, coefficient, confidence, limitations, and reproducer. Master independently rechecks source arithmetic, identity, applicability and tests; only master promotes a rule in ProfessionMechanicsRegistry.json. No self-certification. Master must report rule hypotheses examined / verified / blocked separately from item record first-pass counts.
8. **COMPILE LATER:** After independent QA, only a rule satisfying *all* numeric release gates below can be emitted as data into the FUTURE research/proposed/itemdb.lua by a reviewed deterministic generator. Formula implementations live in ConversionEngine.lua; itemdb.lua holds rule IDs, exact applicability, parameter values and provenance/confidence, never executable arbitrary code. Research JSON and raw experiment archives stay outside the shipped addon. Production migration is a separate user-approved step.

## Strict numerical release gate — every check required
- evidenceStatus = VERIFIED_NUMERIC; applies = VERIFIED_APPLIES; numericTransformValidated = true; applyPolicy = VERIFIED_FOR_COMPILE; rule confidence >=90 with independently corroborated evidence; explicit master review and reproducible passing tests.
- Exact recipeSpellID, input item IDs and output item IDs (where the effect target is output-specific); positive batch size and matching input/output rank or explicit allowed rank sets. Patch bounds and client-build applicability documented, or explicitly approved no-patch-effects condition with provenance. Missing fields BLOCK promotion.
- Formula ID is from a reviewed allowlist with finite numeric parameters and units and a clear effect target. Distinguish ratio, additive, quality transition and expected-input-savings rules; do not treat these as interchangeable.
- All adjustment dependencies must be obtainable for the actual character via supported WoW APIs or explicitly SIMULATED/CACHED_ALT with timestamp. If required live context is absent, decline adjustment and label the reference as not normalized. Do not use source context as current-player data.
- Independently check arithmetic, field invariants and regression snapshots; record test SHA and source claim IDs. Never convert a qualitative source into an arbitrary coefficient.
- Candidate/blocked rules must NEVER appear in the shipped numerical rules section. Existing output baselines still require their *own* field-level confidence; a good modifier cannot rescue a bad baseline.

## Formula effect taxonomy
- OUTPUT_OCCURRENCE adjusts event probability only when a verified probability model exists; never infer expected quantity directly from it without a validated conditional count distribution.
- OUTPUT_UNCONDITIONAL_EXPECTATION adjusts mean per operation; never multiply resulting E by p again.
- OUTPUT_QUALITY uses a tested transition vector across mutually exclusive rank IDs; never value all ranks simultaneously.
- EXPECTED_INPUT_CONSUMPTION applies verified saved reagents to effective input cost/denominator; do not multiply the output vector by saved-reagent chance.
- OUTPUT_ELIGIBILITY requires proof of actual obtainable results before enabling previously absent outputs.
- OPERATION_DURATION affects hourly rates only when modeled explicitly, not per-operation material EV.

## Initial disjoint hypotheses
- **Midnight:** March 31, 2026 gem hotfix: find matched pre/post, same ore/rank/skill/recipe gem cohorts. Current registry records qualitative change but **no known multiplier**.
- **War Within:** prospecting Resourcefulness: empirical saved ore per applicable cast as a function of recipe-specific stat and bonuses; input-consumption effect only.
- **Dragonflight:** Inspiration versus prospecting output quality transitions; separate input-ore rank, output-gem rank and skill threshold.
- **Legacy:** standard vs mass Felslate prospecting (5 vs 20 inputs); confirm distinct spell/recipe and denominators without assuming equal distributions.

These are research questions, not assertions that an effect exists or that any formula has been verified.

## Commands and acceptance
Research QA can run `node research/tests/test_numeric_rules.js` and `node research/tests/test_itemdb_candidate.js` on a repository checkout. These are **static research gates** only, not in-WoW tests. Review source version and repeat after every accepted mechanic change. A compiled example must fail closed if a candidate lacks a documented exact scope or source. No release/merge without approval.
